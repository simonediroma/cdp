# cdp (constructive demolition protocol) — Claude Desktop Plugin

Claude Desktop plugin for coworking on any project spec. Iteratively builds and refines `project-spec.md` through onboarding, demolition, and integration cycles.

## Installation on Claude Desktop

### Method 1 — Marketplace (recommended)

```
/plugin marketplace add simonediroma/cdp
/plugin install cdp@simonediroma-cdp
```

Verify with `/cdp:echo` — if it responds `hello world`, the plugin is active.

---

### Method 2 — Local clone

```bash
git clone https://github.com/simonediroma/cdp.git
```

Open the Claude Desktop configuration file:

- **macOS**: `~/Library/Application Support/Claude/claude_desktop_config.json`
- **Windows**: `%APPDATA%\Claude\claude_desktop_config.json`

Add the plugin to the `plugins` section (create it if it doesn't exist), then restart Claude Desktop:

```json
{
  "plugins": [
    { "name": "cdp", "path": "/absolute/path/to/cdp" }
  ]
}
```

---

### Local test (Claude Code CLI)

```bash
claude --plugin-dir ./cdp
/cdp:echo
```

## Available commands

| Command | Description |
|---|---|
| `/cdp:echo` | Responds with "hello world" — verifies the plugin is active |
| `/cdp:onboarding` | Starts the onboarding interview to create `project-spec.md` |
| `/cdp:derisk` | Sweeps an artifact across every risk lens in one pass and writes the findings to `risk-register.md` — breadth, no interrogation. The complement of `demolish` |
| `/cdp:demolish` | Runs a critical demolition cycle on the current `project-spec.md`, logging what is still dangerous to `risk-register.md` |
| `/cdp:integrate` | Integrates feedback, updates `project-spec.md`, retires closed risks, and promotes the spec's status |
| `/cdp:resume` | Resumes work from the last session |
| `/cdp:export` | Exports `project-spec.md` in a shareable format |
| `/cdp:persona` | Manages project personas |
| `/cdp:session-start` | Initializes a new work session |
| `/cdp:spec-to-code` | Transforms a frozen spec (PRD) into a full AI boilerplate package |
| `/cdp:ticket` | Opens a single Jira ticket from a free-form input — reads the project's real scheme, checks for a duplicate, drafts to `reference/jira-fields.md`, confirms once before writing |
| `/cdp:spike-integrate` | Integrates resolved spike docs into the boilerplate and updates Jira |
| `/cdp:arch-init` | Generates `architecture-context.md` from repo scan, Confluence MCP, and guided interview |
| `/cdp:loop-init` | Opt-in: activates a live isolated-reviewer subagent and a SessionStart automation hook in a project already generated by `/cdp:spec-to-code` |
| `/cdp:design-init` | Generates `design-context.md` — the components of *your* design system relevant to a project, extracted live from wherever it is documented (declared in `project.config.json` → `design_system`) |
| `/cdp:spec-to-ux` | Turns a frozen spec into a reviewed flow/state/IA brief — `ux-brief.md` (PRODUCT) or `journey-brief.md` (BRAND) — with every requirement numbered and a coverage matrix |
| `/cdp:spec-to-wireframe` | Renders a UX brief into a navigable lo-fi wireframe — device frame, screen registry, selectable data profiles, flow map. Greyscale, no design system |
| `/cdp:spec-to-design` | Transforms a frozen spec into static, self-contained HTML mockups faithful to your design system (neutral placeholder tokens when none is configured) |

## Reference files

The plugin uses several context files. Some are generated automatically; others you write once and reuse.

| File | Who creates it | Purpose |
|------|---------------|---------|
| `project-spec.md` | Generated by `/cdp:onboarding` | The spec — source of truth for one feature or project |
| `cdp-memory.md` | Generated by `/cdp:onboarding`, updated by all skills | CDP session memory: defined terms, decisions, session log. Belongs to the plugin, not to the user's project repo. |
| `architecture-context.md` | You write it once per product | Describes the existing product: stack, modules, conventions, design system. Reused across all feature specs. |
| `CLAUDE_MEMORY.md` | Generated by `/cdp:spec-to-code` inside the **user's project repo** | Implementation session tracker for Claude Code (macro status, next task). Different file, different repo, different purpose from `cdp-memory.md`. |
| `docs/deploy-setup.md` | Generated by `/cdp:spec-to-code` (GREENFIELD only), from the Deploy Discovery interview | Step-by-step setup guide for the chosen deploy infrastructure — platform, budget, env vars, domain, rollback. Read by the `M_deploy` macro's Shipping checklist gate. |

---

### When does `architecture-context.md` matter?

| Phase | Commands | Needs architecture-context.md? | Why |
|-------|----------|-------------------------------|-----|
| Spec building | `onboarding`, `demolish`, `integrate` | No (optional) | The spec is about WHAT and WHY — no technical details needed. Useful only in `/cdp:demolish` to check technical feasibility. |
| Boilerplate generation | `spec-to-code`, `spike-integrate` | Yes — **mandatory for FEATURE-ADDITION** | Claude generates real file paths, contextualised macros and precise prompts only if it knows the stack and the modules involved. Without it, prompts contain generic `<path/file>` placeholders. |

For **GREENFIELD** projects (new system from scratch) `architecture-context.md` is optional — the stack is chosen during analysis.

---

### What goes inside `architecture-context.md`

Write it once per product or team. Copy this template and fill it in:

```markdown
# Architecture Context — <Product / Team Name>

## Tech Stack
| Layer | Technology |
|-------|-----------|
| Frontend | <framework + language> |
| Backend | <runtime + framework> |
| Database | <DB + ORM> |
| Auth | <protocol + token mechanism> |
| Deploy | <platform + strategy> |

## Repository Structure
<brief description of main directories and their responsibility>
<e.g. "src/features/ — one folder per domain; src/shared/ — reusable utilities and components">

## Key Modules
| Module | Path | Responsibility |
|--------|------|----------------|
| <name> | <path/to/module> | <what it does — one line> |

## Conventions
- Testing: <framework, location, naming pattern>
- Error handling: <pattern in use — e.g. "Result type", "try/catch at controller boundary">
- Naming: <file, function, variable conventions>
- <any other convention worth knowing>

## Design System (only if the feature has a frontend component)
- Component library: <name + version>
- Key components: <list of most-used ones — e.g. Button, Input, Modal, Table>
- Naming conventions: <e.g. PascalCase, compound names like PrimaryButton>
- Storybook or docs: <link if available>

## What NOT to touch
- <invariant files or modules — e.g. "do not modify src/auth/middleware.ts directly">
- <shared services that require cross-team coordination>
```

**On the design system:** you don't need the full documentation. The component library name, a list of the most-used components, and naming conventions are enough. A Storybook link covers the rest.

---

### How to pass it to the plugin

**Claude Desktop** — attach `architecture-context.md` to the chat before running `/cdp:spec-to-code`. Claude will read it as part of the conversation context.

**Claude Code CLI** — open Claude Code in the repo root. Place the file at `docs/architecture-context.md` or in the root. The plugin reads it directly from the filesystem.

**Hybrid (recommended for teams)** — keep `architecture-context.md` for the stable parts (stack, conventions, design system) and let Claude Code read the actual repo for module-level details specific to each feature. This gives the most precise macro prompts with real file paths.

## Example workflow: from idea to implementation-ready boilerplate

This is the full CDP flow — from a rough idea to a hardened spec and a ready-to-run AI boilerplate for Claude Code or Cursor.

### Step 1 — Build the spec with onboarding

```
/cdp:onboarding
```

CDP interviews you across 10 structured sections (brand, audience, objective, value proposition, messaging, tone, channels, positioning, constraints, limitations) and produces `project-spec.md` v1.0. You answer, CDP formalizes — ideas come from you, not from the AI.

---

### Step 2 — Add personas (optional but recommended)

```
/cdp:persona
```

Define the critical perspectives that will attack the spec during demolition: the end user, the sceptical investor, the engineer who has to build it, the competitor. Each persona has a role, a goal, and a set of objections.

---

### Step 3 — Demolish the spec

```
/cdp:demolish
```

CDP picks one persona and runs a structured critique cycle. It surfaces vulnerabilities (assumptions, ambiguities, contradictions, missing information, feasibility gaps) classified by severity: Critical, Major, Minor. It never modifies `project-spec.md` directly — it only surfaces problems.

Repeat with different personas until you've run at least 3 cycles.

---

### Step 4 — Integrate feedback

```
/cdp:integrate
```

After demolition, you decide which vulnerabilities to resolve, accept, or defer. CDP applies the changes to `project-spec.md` and bumps the version. Minor version for tactical changes (1.0 → 1.1), major version for strategic changes (1.x → 2.0).

Repeat Steps 3–4 until the spec is hardened (no open Criticals, all Majors resolved or accepted with rationale).

---

### Step 5 — Export the spec (optional)

```
/cdp:export
```

Generates a formatted `.docx` file of `project-spec.md` — ready to share with stakeholders, clients, or the team.

---

### Step 6 — Generate the implementation boilerplate

```
/cdp:spec-to-code
```

Once the spec is frozen (demolition-complete), CDP reads `project-spec.md` and generates a full AI boilerplate package.

For **GREENFIELD** projects, before decomposing into macros, CDP runs a **Deploy Discovery** interview: it proposes a first deploy setup (platform, strategy, rough cost) based on the stack and PRD, then refines it with a few targeted questions — budget ceiling, existing/preferred provider, region or compliance constraints, domain. You confirm before it feeds the rest of the boilerplate; CDP formalizes the decision, it doesn't pick it for you.

**For Claude Code:**
- `CLAUDE.md` — operating rules, development principles (Doubt-Driven Review, TDD, 5-axis gate), architectural constraints
- `CLAUDE_MEMORY.md` — session state tracker (gitignored, updated after each task)
- `docs/architecture.md` — stack, repo structure, I/O schema, environment variables
- `docs/deploy-setup.md` — step-by-step setup guide for the chosen deploy infrastructure (GREENFIELD only, from the Deploy Discovery interview)
- `prompts/M0_scaffold.md`, `prompts/M1_*.md`, ..., `prompts/M_deploy.md` — one implementation prompt per macro, ordered and sized (LOW/MEDIUM/HIGH/DEPLOY risk)
- `HANDOFF.md` — execution order and onboarding instructions

**For Cursor:**
- `.cursor/rules/01-operative.mdc` — always-active operative rules + "next task" trigger
- `.cursor/rules/02-memory.mdc` — always-active session memory (auto-updated by Cursor)
- `.cursor/rules/03-refs.mdc` — always-active technical references
- `.cursor/rules/MN-<name>.mdc` — one glob-activated rule per macro, including `M_deploy` if triggered
- `SETUP.md` — setup and usage instructions

`docs/deploy-setup.md` is shared by both tracks — same file, read by either `CLAUDE.md` or `.cursor/rules/03-refs.mdc`.

**A third, opt-in format:** `claude-code-agent-skills` — same file structure as the Claude Code track above, but the engineering-discipline sections (Doubt-Driven Review, TDD, Pre-PR Gate) are replaced with references to the real skills from Addy Osmani's [`agent-skills`](https://github.com/addyosmani/agent-skills) plugin (e.g. `agent-skills:doubt-driven-development`) instead of embedded approximations. Richer and genuinely dynamic — including real context-isolated adversarial review, which the two self-contained tracks cannot faithfully reproduce — but requires `agent-skills` installed in the session working the generated macros, and accepts that it has no version-stability guarantee. See `skills/spec-to-code-update/references/agent-skills-reference-map.md` and `document/osmani-agent-skills-gap-analysis.md` for the full rationale.

The boilerplate supports both **GREENFIELD** (new project from scratch) and **FEATURE-ADDITION** (adding a feature to an existing codebase) modes. Macros in SPIKE PENDING state generate a `docs/spike-MN.md` investigation template instead of an implementation prompt. The `M_deploy` macro (non-trivial CI/CD) closes with a **Shipping checklist** gate instead of the 5-axis-only review — it verifies the deploy actually matches `docs/deploy-setup.md`: env vars set on the platform, health check passing, rollback verified, cost within budget.

---

**End result:** a Claude Code or Cursor session that knows exactly what to build, in what order, at what risk level — without any manual context setup.
