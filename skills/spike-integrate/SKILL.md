# Spike Integrate

Integrates resolved spike investigation documents into the existing boilerplate. A spike is resolved when a `docs/spike-MN.md` file exists with a clear decision and technical constraints.

**This skill operates on an existing boilerplate** — run `/cdp:spec-to-code` first.

---

## Step 1 — Detect resolved spikes

Scan `docs/spike-M*.md`. These files are created by `/cdp:spec-to-code` as stubs — the developer fills them in after the investigation.

For each file found, read its **`Kind`** first — it decides how the spike is integrated. A file with no `Kind` line predates the field and is `INVESTIGATION`.

| Kind | Resolved when | Integration |
|---|---|---|
| `INVESTIGATION` | `Status: RESOLVED`, all "Expected output" sections filled in | rewrite the macro (Step 2) |
| `DECISION` | `Status: RESOLVED`, every `dN` has **Chosen** and **PRD section to update** filled | apply a diff to the drafted macro (Step 2b) |

- **`Status: OPEN`** (or `[TO BE FILLED]` sections still empty) → not resolved, skip it and flag it at the end. For a DECISION, the **Generator's default** is never applied in the author's place: an unanswered decision stays OPEN.
- **`Status: RESOLVED`** → ready to integrate.

For each **resolved INVESTIGATION** spike, read:
- Which macro is unblocked
- The decision made and the discarded alternative
- Technical constraints discovered
- Files and patterns found
- New acceptance criteria (if any)
- Impact on other macros

If no spike files exist at all: stop and explain that `/cdp:spec-to-code` creates `docs/spike-MN.md` stubs automatically — ask whether to re-run it or whether the user wants to provide the files manually.

If spike files exist but all are still OPEN: list them with their open questions and stop — nothing to integrate yet.

---

## Step 2 — Rewrite the unblocked macros (INVESTIGATION)

For each resolved INVESTIGATION spike, rewrite the corresponding macro using the correct template (LOW/MEDIUM/HIGH) from `references/boilerplate-formats.md`.

**Claude Code:** update `prompts/M<N>_<name>.md`.
**Cursor:** update `.cursor/rules/MN-<name>.mdc`.

Incorporate from the spike doc:
- **Context section**: add the decision made and the discarded alternative
- **Existing modules to read first**: add files/patterns discovered during the spike
- **Notes for Claude Code / Cursor**: add technical constraints as explicit notes
- **Acceptance criteria**: add any new criteria that emerged from the spike
- **Risk level**: assign the correct level (LOW/MEDIUM/HIGH) based on what the spike revealed — the level may differ from what was originally estimated

The macro's Macro Status row in `CLAUDE_MEMORY.md` / `02-memory.mdc` already stores this file's canonical path (see Step 3). Rewriting the file in place does not change that path — if, and only if, you also rename the file (e.g. the spike renamed the macro), update the stored path in the same edit so the row and the file on disk never diverge.

---

## Step 2b — Apply decisions to drafted macros (DECISION)

The macro prompt already exists in full — do not rewrite it. For each `dN` of the spike:

1. Find every line marked `DECISION PENDING (spike-M<N>-d<k>)` in the macro file and replace it with the text of the chosen option — in acceptance criteria and in the DDR. Touch nothing else.
2. If the spike's **Impact on other macros** names other macros, apply the same substitution there, and nothing beyond it.
3. Check that no `DECISION PENDING` line referencing this spike remains in any prompt.
4. Remind the author of the **PRD section to update** — the decision must go back into the PRD, or a regeneration resurfaces it. This skill does not edit the PRD.

---

## Step 3 — Update memory

**Claude Code:**
In `CLAUDE_MEMORY.md`, find the line with `⏳ M<N>` (`SPIKE PENDING` or `DECISION PENDING`) and replace with `[ ] M<N>` (status: to implement, spike resolved), appending the canonical `` `prompts/M<N>_<name>.md` `` path — the same file rewritten in Step 2 — as the trailing path on the row. Never mark a macro `[ ]` without a path pointing at a file that actually exists.

**Cursor:**
In `.cursor/rules/02-memory.mdc`, same replacement, with the row's trailing path pointing at `.cursor/rules/MN-<name>.mdc`.

Then check `HANDOFF.md` / `SETUP.md`: if the spike changed the dependency between macros, update the execution order.

---

## Step 4 — Record scope changes locally (mandatory, before Jira)

A DECISION spike logs an entry here **only if the chosen option changes scope** (new criteria, extra modules, a different risk level) — picking one of the options the drafted prompt already anticipated is not a scope change.

A scope change occurs when:
- New acceptance criteria emerged that weren't in the original PRD
- The macro now touches additional modules not listed in the original story
- The risk level changed significantly (e.g., LOW → HIGH)
- A new macro must be added that didn't exist in the original plan

If none of the resolved spikes triggered a scope change, skip to Step 5.

Otherwise, `docs/change-requests.md` is the **primary record** of the change — written unconditionally, whether or not Jira is connected. A Jira ticket (Step 5c) is an optional mirror added on top of it afterward, never a substitute for it. This is the same local-first pattern `docs/spike-MN.md` already uses.

1. If `docs/change-requests.md` doesn't exist yet, create it with this header:
   ```markdown
   # Change Requests

   Append-only log. One entry per scope change discovered after the PRD was frozen.
   This file is the primary record — a Jira ticket, if one exists, mirrors an entry
   here and links back to it; it is never the only place a change is recorded.
   ```

2. For each scope change, append an entry (count existing `## CR-` headings and increment `<N>`; never edit or remove a prior entry):
   ```markdown
   ---

   ## CR-<N> — M<N> — <macro title> — <what changed in one line>

   **Date:** <date>
   **Status:** APPLIED

   **Original requirement (from PRD)**
   <original AC or constraint from the original story>

   **Changed requirement**
   <new AC or constraint after spike resolution>

   **Reason**
   <what the spike discovered that forced the change>

   **Impact**
   - Macro affected: M<N>
   - Other macros impacted: <list or "none">
   - PRD sections to update: <list sections by name>

   **Action taken**
   - [x] Macro prompt M<N> updated / generated (Step 2 for an existing macro, Step 6.2 for a newly created one)
   - [ ] PRD section <N> updated
   - [ ] Re-run /cdp:spec-to-code for affected macros if scope change is significant

   **Jira:** <link, filled in during Step 5c if Jira is connected> — otherwise "not connected — this entry is authoritative"
   ```

This step is not gated on Jira availability and does not skip silently — a scope change with no `docs/change-requests.md` entry is the exact failure mode this step exists to prevent.

## Step 5 — Jira (if MCP available, optional mirror)

→ **Read `${CLAUDE_PLUGIN_ROOT}/reference/jira-fields.md` before drafting anything.** It is the single source for
the Summary format, the per-type description skeletons and the label taxonomy. Do not restate its rules here and
do not work from memory of them — a ticket drafted without reading it is the exact failure this pointer exists to
prevent.

**Detect availability by trying the call** — `getVisibleJiraProjects` — never by testing for a tool name (`${CLAUDE_PLUGIN_ROOT}/reference/mcp-servers.md`). If it fails, say so and skip without blocking — the record
from Step 4 already stands on its own. Jira is a **mirror** of `docs/change-requests.md`, never a substitute for it.

**Before the first create**, read the project's real scheme (`getJiraProjectIssueTypesMetadata`, then
`getJiraIssueTypeMetaWithFields` for the types you'll use). Never assume `Story` and `Task` exist — flatten to what
the project actually offers, and say so in the ticket when the scheme forces a deviation.

**Every ticket below carries `AI-ASSISTED` plus exactly one category label**, passed through
`createJiraIssue`'s `additional_fields`. After each create, **re-read the issue with `getJiraIssue`** and confirm
the labels landed — the create response does not echo them.

**One ticket, one go-ahead.** Show the full draft, wait, then create. Never batch.

For each integrated spike:

**a) Close the spike ticket** (INVESTIGATION or DECISION ticket alike)
- Set status to Done
- Add comment: "Spike resolved. Decision: `<decision in one line>`. See `docs/spike-M<N>.md`." — for a DECISION, also name the PRD section to update

**b) Create the unblocked Story**

Category per `jira-fields.md`: `[FEAT]` when the macro delivers user-facing capability, `[CHORE]` when it is
infrastructure, migration or tooling. Label accordingly — `Product-Evoluzione` for a new user-facing macro,
`Tech-Evoluzione` or `Tech-BAU` for technical work. Confirm the category at the gate; don't assume it.

```
Summary: [FEAT] <Component> — M<N> <macro title>
Labels:  Product-Evoluzione, AI-ASSISTED        ← confirm the category; AI-ASSISTED is never optional
Epic link: <parent epic>

**User story**
As a <persona>, I want <capability from the macro>, so that <benefit>.

**Context & links**
Macro M<N>, unblocked by spike `docs/spike-M<N>.md`. Depends on M<N-1>. Risk level: <level assigned after spike>.

**Edge cases**
<the unhappy paths the spike surfaced, if any>

**Acceptance criteria**
- [ ] <criterion from the rewritten macro>
- [ ] <criterion>
- [ ] Test: `<exact command>`
- [ ] Build: `<exact command>`

**Definition of Done**
- Pre-PR gate passed (see macro prompt)
- PR reviewed and merged
- CLAUDE_MEMORY.md / 02-memory.mdc updated (if the project tracks CLAUDE_MEMORY.md in git — committed memory strategy, used for Claude Code web/desktop — the memory update is committed and pushed, not just edited locally)

**Notes**
<key constraints discovered by the spike>
```

The macro number lives in the **title**, not in the tag slot — the brackets hold the tag, which is what the board
filters on.

**c) Change Request — only if Step 4 wrote a `docs/change-requests.md` entry**

Do not compose this from scratch — mirror the `CR-<N>` entry already written in Step 4. A CR **inherits the
category of the macro it changes**: it is a change to that unit, so it sits on the same axis.

```
Summary: [CHORE] <Component> — M<N> CR-<N>: <what changed in one line>
Labels:  <same axis as the macro it changes>, AI-ASSISTED

**Need (why now?)**
<Reason — copied verbatim from the docs/change-requests.md entry>

**Technical activity (high level)**
<Original requirement → Changed requirement — copied verbatim>

**Impact / risks**
<Impact — copied verbatim>

**Acceptance criteria**
<Action taken — copied verbatim>

**Local record:** docs/change-requests.md#CR-<N>
```

`CR-<N>` goes in the title, never in the brackets, and **there is no `change-request` label** — that word is not in
the taxonomy, and inventing it creates a parallel label nobody filters on. What kind of ticket this is, the
Summary already says.

After creating the Jira ticket, go back and fill in the `**Jira:**` line of the `CR-<N>` entry in
`docs/change-requests.md` with the ticket link, and add a link to it in the Story description under a
"Change Requests" heading.

## Step 6 — Exit check

After integrating all available spikes:

1. Are there still macros marked `⏳ SPIKE PENDING` in memory?
   - **Yes**: list them with their open questions (from the corresponding `docs/spike-MN.md` stubs), separating INVESTIGATION (the developer investigates) from DECISION (the PRD author answers — show the generator's default, never apply it). Remind whoever owns each to fill in the stub and re-run `/cdp:spike-integrate`.
   - **No**: print "All spikes resolved. Boilerplate ready for implementation."

2. Did any spike create a new macro that didn't exist before?
   - **Yes**: this is a Change Request macro — it does not get a Macro Status row until its prompt file exists. In order:
     1. Assign a risk level (LOW/MEDIUM/HIGH) per the same criteria as `/cdp:spec-to-code` Step 3.
     2. **Generate its prompt file** — `prompts/M<N>_<name>.md` (Claude Code / claude-code-agent-skills) or `.cursor/rules/MN-<name>.mdc` (Cursor) — using the correct template from `references/boilerplate-formats.md` for that risk level, exactly as `/cdp:spec-to-code` Step 6 would have done had this macro existed at generation time. This step is mandatory and is not optional even under time pressure — a macro without a generated prompt file must not be added to memory as if it were ready to implement.
     3. Only now add the macro to `CLAUDE_MEMORY.md` / `02-memory.mdc`, with the file path from step 2 on the row, per the same format used in Step 3 above.
     4. Create the Jira story **per Step 5b** — same conventions, same gate, same post-create verification; a ticket opened from this branch is not exempt from `reference/jira-fields.md`. Link it to the `docs/change-requests.md` entry from Step 4 and to its Jira mirror if one exists, then update `HANDOFF.md` / `SETUP.md`'s execution order.
   - Before printing the final summary, re-scan every `[ ]` row in the Macro Status list (not just the ones touched this run) and confirm each stored path resolves to a real file. Flag any mismatch instead of silently leaving it — this is the exact failure mode that let macros run without a prompt file in the past.

3. Cross-check `docs/change-requests.md`: every scope change identified this run must have a `CR-<N>` entry, independent of whether Jira was reachable. Flag any scope change that was actioned (macro rewritten, prompt generated) without a matching local entry — the code changed but the "why" wasn't written down.

4. Print a final summary:
   ```
   Spike integration complete
   ──────────────────────────
   Spikes integrated:      N (INVESTIGATION N · DECISION N)
   Macros unblocked:       M<list>
   Change Requests logged: N (docs/change-requests.md — N mirrored to Jira)
   Remaining spikes:       N (list if any)
   Status: READY / PENDING SPIKES
   ```
