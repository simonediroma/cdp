# Skill: Loop Init

`/cdp:spec-to-code` generates a boilerplate whose Doubt-Driven Review is self-review (same agent, same context) and whose "next task" cycle only ever starts when a human types the trigger phrase. This skill closes both gaps for real, in the project you run it in — it writes live Claude Code configuration, not prose describing what someone could set up later.

Two independent additions, each opt-in with its own explicit confirmation. Never assume a default; never enable either without the user saying so.

---

## Precondition

Check that `CLAUDE.md`, `CLAUDE_MEMORY.md`, and `prompts/` exist in the current repo. If any is missing, tell the user to run `/cdp:spec-to-code` first and stop — there is nothing for this skill to attach to.

---

## Step 1 — Isolated reviewer subagent (detect-then-ask)

**Detect:** read `CLAUDE_MEMORY.md` and `prompts/`. Does at least one macro carry HIGH or FRONTEND HIGH risk? If none, skip this step silently — nothing would invoke the subagent.

**Ask**, only if at least one such macro exists:

> "This project has `<N>` HIGH-risk macro(s): `<list — code + title>`. Their Doubt-Driven Review currently runs as self-review — the same agent that wrote the code also lists the doubts. I can generate a native Claude Code subagent (`.claude/agents/spec-reviewer.md`, invoked via the Task tool) that runs in a genuinely separate context: it sees only the diff and the macro's written acceptance criteria, never your reasoning or CLAIM. Purely additive — declining leaves the existing self-review section exactly as it is. Generate it?"

Wait for an explicit yes/no. Do not proceed on silence or a vague reply.

**If yes:**

1. Write `.claude/agents/spec-reviewer.md`:

```markdown
---
name: spec-reviewer
description: Read-only adversarial reviewer for HIGH-risk macros. Invoke via the Task tool after implementing a HIGH-risk macro, before opening the PR, passing ONLY the diff and the macro's written acceptance criteria — never your own reasoning, CLAIM, or justification. Use PROACTIVELY whenever a HIGH-risk (or FRONTEND HIGH) macro is about to reach its Pre-PR Gate.
tools: Read, Grep, Glob
---

You are an independent, adversarial code reviewer. You have NOT seen the reasoning that produced the diff you are about to review, and you must not ask for it or infer it from the caller's framing — that is the point: your value comes from having no stake in defending the original decisions.

## What you receive
Exactly two things, no more:
1. The diff (or the list of changed files, read with the Read tool) for one macro.
2. That macro's written acceptance criteria, verbatim from its `prompts/MN_<name>.md` file.

If the invocation also includes an explanation of *why* the implementer made a choice, disregard that framing. Review the code and criteria as if they arrived with no cover letter.

## What you do NOT have
- No Edit or Write tools. You cannot fix anything — only find and report. Roles between "wrote it" and "checked it" stay separate.
- No access to the conversation that produced the diff.

## Review method
For each axis, produce findings with a verdict:
- **CONFIRMED** — traced to a concrete line/behavior; state the exact failure scenario.
- **PLAUSIBLE** — real concern, not fully confirmable from the diff alone.

Axes (same 5 as the project's Pre-PR Gate): Correctness, Security, Readability, Performance, Surgical.

## Output format

## Spec Reviewer — M<N> verdict

### Correctness
- [CONFIRMED|PLAUSIBLE] <finding> — <exact scenario that breaks>

### Security
### Readability
### Performance
### Surgical

## Overall
BLOCK PR | PROCEED — <one-line reason>

`BLOCK PR` if there is at least one CONFIRMED finding on Correctness or Security. Otherwise `PROCEED`, listing PLAUSIBLE findings as follow-ups, not blockers. Do not soften a CONFIRMED finding into a suggestion.
```

2. In `CLAUDE.md`, find the existing `### 6. Doubt-Driven Review — for high-risk decisions` section and replace it in place with:

```markdown
### 6. Doubt-Driven Review — isolated (subagent-based)

**Activate when:** the macro is HIGH, FRONTEND HIGH, or was risk-escalated to HIGH.

Do not self-review these. Before opening the PR:
1. Finish the implementation and let it pass its own tests/build.
2. Invoke the `spec-reviewer` subagent via the Task tool, passing **only**:
   - The diff (or exact list of changed files)
   - The macro's `## Acceptance criteria` section, verbatim
   Do **not** pass your CLAIM or reasoning — the isolation only holds if it never sees why you think the code is correct.
3. Read the verdict.
   - `BLOCK PR` (any CONFIRMED on Correctness/Security): fix, then re-invoke on the updated diff. Do not proceed on `BLOCK PR`.
   - `PROCEED`: continue to the Pre-PR Gate. Note PLAUSIBLE findings in the PR description as follow-ups.

See `.claude/agents/spec-reviewer.md` for what the subagent actually checks.
```

3. For every HIGH/FRONTEND HIGH macro's `prompts/MN_<name>.md`, replace its embedded `## Doubt-Driven Review — run before writing code` block (CLAIM/DOUBT/RECONCILE prose) with:

```markdown
## Doubt-Driven Review — isolated (run before opening the PR)

Do not self-review. After implementation passes its own tests/build:
1. Invoke the `spec-reviewer` subagent (Task tool) passing ONLY this file's `## Acceptance criteria` section and the diff — never your reasoning.
2. If it returns `BLOCK PR`: fix, then re-invoke on the updated diff.
3. If it returns `PROCEED`: continue to the Pre-PR Gate below.
```

If the project uses the `claude-code-agent-skills` track instead (an `## Engineering Discipline` section naming `agent-skills:doubt-driven-development` rather than an embedded CLAIM/DOUBT/RECONCILE block), replace only the `agent-skills:doubt-driven-development` line with a pointer to the isolated subagent above — leave every other `agent-skills:x` reference (TDD, security, code review) untouched.

**If no:** touch nothing. Do not raise this again in the same session.

## Step 2 — SessionStart automation hook (detect-then-ask)

**Ask, once per project, regardless of risk composition:**

> "I can add a real `SessionStart` hook to `.claude/settings.json` that, every time you open Claude Code on this repo, automatically checks `CLAUDE_MEMORY.md` and surfaces the next-task plan — you won't need to type `what's the next task?` yourself. It only auto-continues for LOW/MEDIUM-risk macros; if the next macro is HIGH, FRONTEND HIGH, or DEPLOY, it will tell you a manual session is required instead of proceeding. To be clear about what this is *not*: this doesn't run unattended overnight — someone still has to open the session for the hook to fire — and it costs real tokens each time it does. No CI, no secrets, nothing runs outside a session you started. Add it?"

Wait for an explicit yes/no.

**If yes:**

1. Write `.claude/hooks/next-task-check.sh` (make it executable):

```bash
#!/usr/bin/env bash
# Auto-surfaces the next-task plan at SessionStart, gated by risk level.
MEMORY_FILE="CLAUDE_MEMORY.md"
[ -f "$MEMORY_FILE" ] || exit 0

NEXT_MACRO_LINE=$(grep -m1 "Next macro:" "$MEMORY_FILE")
[ -n "$NEXT_MACRO_LINE" ] || exit 0

MACRO_CODE=$(echo "$NEXT_MACRO_LINE" | grep -oE 'M[0-9_]+[A-Za-z0-9_]*' | head -1)
[ -n "$MACRO_CODE" ] || exit 0

PROMPT_FILE=$(ls prompts/${MACRO_CODE}_*.md 2>/dev/null | head -1)
RISK=""
if [ -n "$PROMPT_FILE" ]; then
  RISK=$(grep -m1 -oE 'LOW|MEDIUM|HIGH|FRONTEND HIGH|FRONTEND|DEPLOY' "$PROMPT_FILE" | head -1)
fi

case "$RISK" in
  LOW|MEDIUM)
    echo "Next macro ($MACRO_CODE) is $RISK risk — auto-continuing. what's the next task?"
    ;;
  HIGH|"FRONTEND HIGH"|DEPLOY)
    echo "Next macro ($MACRO_CODE) is $RISK risk — manual session required, not auto-continuing. Open with \"what's the next task?\" yourself when ready to review it."
    ;;
  *)
    echo "Could not determine risk level for $MACRO_CODE — manual session required, not auto-continuing."
    ;;
esac
```

2. Merge — never overwrite — a `SessionStart` entry into `.claude/settings.json`:
   - If the file exists, read it, parse the JSON, and append this hook into the existing `hooks.SessionStart` array (create that key if absent) without touching any other key or existing hook entry.
   - If it doesn't exist, create it with only this entry:

```json
{
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "bash .claude/hooks/next-task-check.sh"
          }
        ]
      }
    ]
  }
}
```

**If no:** do not touch `.claude/settings.json` or create the hook script.

## Step 3 — Summary

Report plainly what was activated and what wasn't (each of Step 1 and Step 2, independently). For anything activated, say how to undo it:
- Isolated subagent: delete `.claude/agents/spec-reviewer.md`, and manually revert the `CLAUDE.md`/`prompts/` sections if desired (this skill does not track a rollback diff).
- SessionStart hook: remove its entry from `.claude/settings.json`'s `hooks.SessionStart` array, delete `.claude/hooks/next-task-check.sh`.
