# Output Contract — `spec-to-design`

Exact structure and rules for everything Steps 4-7 of `SKILL.md` produce. Referenced by section name — don't rename the headings below.

---

## File contract

```
design-mockups/
├── index.html                    # journey cards + per-screen matrix + report
├── assets/
│   └── ds-tokens.css             # copy of design-tokens.css, or of the neutral fallback
├── 01-<screen-name>-a.html
├── 01-<screen-name>-b.html
├── …
├── 01-<screen-name>-e.html
├── 02-<screen-name>-a.html
└── …
```

One file per screen × journey letter. The component list and DS constraints behind a given screen number are identical across its five letters — only the composition choices from the journey profile (Step 3b) differ.

This is the **GREENFIELD** structure. For **FEATURE-ADDITION**, see "File contract — FEATURE-ADDITION" below.

Binding rules for every screen file:

1. **Self-contained**: complete HTML5, CSS inline in `<style>`, no framework, no build step, no external dependency except a web-font `@import` if the DS's font requires one. Must open with a double click.
2. **No hardcoded styling**: every color, spacing value and font-size comes from a `ds-tokens.css` custom property (`ds-rules.md` U2).
3. **Zero JavaScript**, unless it shows an interactive state the spec explicitly names (e.g. opening an FAQ accordion). Then: inline, a few lines, no library. The journey navigation bar is plain `<a>` links.
4. **`data-ds-component`** on every block that represents a DS component:
   `<div data-ds-component="Card" data-ds-ref="<identifier from design-context.md>" data-ds-variant="Featured">`
   Makes the mockup inspectable and enables automated coverage checks.
5. **`data-ds-gap="true"`** on every block built outside the DS, paired with an inline comment per rule 13.
6. **`data-journey="A"`** on the page's root wrapper, naming which journey letter this file belongs to. Distinct from `data-ds-variant`.
7. **Provenance banner** at the top of every page, in a fixed, non-printable `<div>`:
   *"Mockup generated by spec-to-design · Journey B — two-column layout, featured cards · tokens: <DS name> snapshot DD/MM/YYYY | neutral fallback · N DS components, M off-DS elements · not production code"*
8. **Journey navigation bar**, in the same fixed area: "← Back to index", "← Previous screen" / "Next screen →" **within the same journey letter** (omitted, not dead, at the ends), and "Screen N of M".
9. **Responsive**: media queries at the DS's documented breakpoints, mobile-first (`ds-rules.md` U6). Don't invent others without declaring them.
10. **Content**: realistic text in the spec's output language, consistent with its Tone of Voice. **Never lorem ipsum** — a mockup with lorem ipsum can't be reviewed. If a copy engine is installed, use it — see `CLAUDE.md` § "External copy engine".
11. **Device frame**: wrap the page in the chrome from `html-patterns.md` § "Device frame" — a browser bar at ≥768px, a phone bezel at <768px. One `.ds-device-frame` wrapper, CSS media queries only. Applies to every PRODUCT screen; omit only for a BRAND landing meant to read edge-to-edge.
12. **Site chrome**: every PRODUCT screen carries the site Header and Footer around its content, inside the device frame — logo (always a GAP placeholder, U4), primary nav, CTA (adapting to the Header's mobile variant, never just disappearing), footer legal links. Omit only when the screen lives in another shell (embedded widget, iframe, native app) — and declare it.
13. **Inline gap comments**: every `data-ds-gap="true"` block, and every token value estimated for this specific use, gets a one-line CSS comment explaining what was assumed and why.

### `index.html` structure

- **Journey cards** — one per letter, each with its one-line direction and a "Start journey" link to its first screen.
- **Screen matrix** — screens as rows, journey letters as columns, every cell a direct link.
- **Report** — the Step 7 final report, in a dedicated always-visible section.

## File contract — FEATURE-ADDITION

```
design-mockups/
├── index.html                    # variant cards, before/after side-by-side, report
├── assets/
│   └── ds-tokens.css
├── before.png                    # <CURRENT_STATE> capture — omitted if "approximated"
├── 01-<feature-name>-a.html
├── 01-<feature-name>-b.html
└── 01-<feature-name>-c.html      # only if a third variant was confirmed
```

All binding rules 1-13 apply in full. Two more:

14. **Before/after in `index.html`**: each variant's card shows `before.png` (or the "approximated, no screenshot available" note) side-by-side with a link to that variant's file.
15. **New-element marker**: the block introducing the new element carries `data-ds-new-element="true"` — what lets a reviewer spot the delta at a glance.

Provenance banner, feature-addition form: *"Mockup generated by spec-to-design · Feature-addition, variant B — collapsible block after the form, using Accordion · current state: fetched DD/MM/YYYY | user-provided screenshot | approximated (declared) · tokens: … · N DS components, M off-DS elements · not production code"*

## Final report

In `index.html` (a dedicated, always-visible section) **and** repeated in chat. **GREENFIELD:**

- The journeys, each with its one-line direction and which parts of any PO guidance it incorporates
- Screen list per journey, with relative links
- DS components used, with links to their documentation (from `design-context.md`)
- **Explicit discrepancies**: for every element not found in the DS or hand-built, what was assumed and why
- **Estimated vs. verified tokens**, with the snapshot date — or that the neutral fallback was used
- Do & Don't that changed the result relative to the user's literal request
- Empty spec sections that produced placeholders
- Whether `design-context.md` was used, or the fallback seed + `ds-rules.md`
- GAP count — must match the `data-ds-gap="true"` blocks, identical across all journeys of the same screen

**FEATURE-ADDITION:**

- The 2-3 variants, each alongside `before.png` (or the approximated note)
- **Current state capture**: source and date
- DS components used, with documentation links
- **Explicit discrepancies**
- Do & Don't that changed the result
- **Any real session/customer data found in a capture**, and confirmation it was replaced in every output file
- Whether `design-context.md` was used
- GAP count, and exactly one `data-ds-new-element="true"` block per variant file
